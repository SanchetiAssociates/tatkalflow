# PGlite ↔ PostgreSQL compatibility

TatkalFlow uses **PGlite** (PostgreSQL 17 compiled to WASM) for local development
and automated tests, and **PostgreSQL 15+** in production. The goal is that
moving to production changes only `DATABASE_URL`.

## How it's wired

PGlite is served over the real Postgres wire protocol by
`@electric-sql/pglite-socket` (`npm run db:dev`, or in-process in tests). The
app, Prisma migrations and pg-boss all connect through the standard `pg`
driver (`@prisma/adapter-pg`), exactly as they will against PostgreSQL. There
is no PGlite-specific code path in `src/`.

| Concern | Dev / test (PGlite) | Production (PostgreSQL) |
|---|---|---|
| Driver | `pg` via `@prisma/adapter-pg` | same |
| Migrations | `prisma migrate deploy` | same |
| Queue | pg-boss (verified: create, delayed start, idempotent `id`, retry → dead-letter) | same |
| New migrations | `npm run db:new-migration -- <name>` (throwaway PGlite shadow DB) | same SQL files |

## Rules the schema follows

- **UUIDs are generated by Prisma** (`@default(uuid())`), not `gen_random_uuid()` or the `uuid-ossp`/`pgcrypto` extensions.
- **No extensions** (no `citext`, `pgcrypto`, PostGIS, `pg_trgm`). Case-insensitive station search uses a normalised `search_text` column.
- **No partial or expression indexes, triggers, stored procedures or RLS.** Uniqueness that would normally need a partial index (e.g. mobile numbers of soft-deleted users) is handled by tombstoning the value on deletion.
- **Only core types:** `uuid`, `varchar`, `text`, `int`, `boolean`, `date`, `timestamptz(3)`, `jsonb`, enums.
- **All instants are UTC `timestamptz`.** Calendar dates (journey date) are `date`. IST conversion happens in application code via the rules service, never in SQL.
- **Time windows use the application clock.** Rows that participate in rate-limit windows (`otp_sessions.created_at`, `locked_at`) are stamped by the service clock, not `now()`, so tests with a fake clock and production behave identically.

## Known differences to keep in mind

1. **Concurrency.** PGlite executes one query at a time; the socket server multiplexes connections (`maxConnections`) by queueing. Transactions are correct but there's no real parallelism, so **lock-contention and throughput behaviour must be load-tested on real PostgreSQL** before launch. Keep `DATABASE_POOL_MAX` ≤ 5 against PGlite.
2. **`LISTEN/NOTIFY`.** Not relied upon. pg-boss is used in polling mode.
3. **Advisory locks.** pg-boss uses them for maintenance; verified working on PGlite, but single-process only in dev.
4. **Extensions.** If a future feature needs one (e.g. `pg_trgm` for fuzzy station search), it must be available on the production host *and* loadable in PGlite, or be gated behind a feature flag with a portable fallback. Document it here.
5. **Durability.** `.pglite/dev` is a convenience store for development. It is not a production database; do not back it up or deploy it.
6. **Supabase.** Compatible: Supabase is plain PostgreSQL. Use the direct (session-mode) connection string for migrations and pg-boss; the transaction pooler (port 6543) is not compatible with pg-boss.
